# 01 — Matching accuracy evaluation tool

Status: ready-for-agent
Type: task
Blocked by: 14
Spec: [matching-evaluation spec](../../matching-evaluation/spec.md)

`matchJob` has deterministic fake-model tests, but its real accuracy and threshold calibration have never been measured (README, Matching section). The fixed 0.2/0.8 probability bands and the ±10-point skill-coverage band are unvalidated.

Build an opt-in tool that measures how often matching agrees with the job seeker's own judgement:

1. **Capture.** Given a vacancy URL and the job seeker's verdict, the tool fetches the vacancy detail through its search source and stores a snapshot with the label in the workspace.
2. **Run.** The tool runs real matching over every stored vacancy within a cost cap and writes a report: agreement, where it disagreed, and cost.

Labelling the real set, recording the baseline and deciding on band changes is issue 35.

Done when the tool exists, its offline tests pass, and typecheck, lint, tests and build pass.

## Comments

### Triage — 2026-10-24

> *This was generated by AI during triage.*

Redundancy check: there is no evaluation script, labelled set or benchmark in `web/`. The old Python framework's `evaluate.py` on `origin/main` is its rule matcher, not an accuracy measurement. Not implemented.

Decisions from grilling:

- **Split.** This issue is the tool. Issue 35 (human) labels about 40 vacancies, runs the baseline and decides on the bands.
- **Storage.** The labelled set lives in the job seeker's workspace and is never committed: real vacancy text and the real profile stay private. A small fictional sample set is committed only for offline tests.
- **Capture.** Capture takes a vacancy URL. Each search source may expose an optional "reference from URL"; a URL no source claims is refused. The vacancy detail is fetched through the source and stored as a snapshot, so runs stay reproducible after a listing closes.
- **Labels.** Labels are given on the command line, never by editing files:
  - a required expected Match outcome;
  - optional expected results for named criteria;
  - a free-text note.

  Re-capturing with a relabel flag replaces the label and keeps the snapshot.
- **Format.** One JSON file per vacancy (job detail snapshot in the existing schema plus label, `schemaVersion: 1`). A set file holds the candidate snapshot.
- **Candidate snapshot.** Labels refer to a snapshot of the matching inputs (search configuration and profile skills) stored with the set. The run uses the snapshot and warns when it differs from the current saved configuration.
- **Commands.** Bun scripts, named so `bun test` never collects them, and excluded from CI.
  - Both take a required `--workspace`.
  - The run takes a required `--max-usd`, plus `--allow-unpriced` and `--dry-run` (fake decision model, no cost).
- **Cost cap.** The run stops before the next call once reported cost reaches the cap. Unpriced calls count as reaching it unless allowed.
- **Failures.** Same policy as the search workflow (ADR 0009). A per-vacancy evaluation error is recorded as an error row, excluded from agreement, and the run continues. An outage, a rate limit or the cost cap stops the run and still writes a partial report.
- **Report.**
  - Header: matching rules version, decision model identity (from issue 14), and the model the responses reported, with any mismatch flagged.
  - Scores: three-outcome confusion matrix; agreement overall and excluding needs-clarification; per-criterion confusion for labelled criteria.
  - One row per vacancy: expected, actual, differing criteria, note.
  - Cost: total cost and unpriced call count.

  It is written to the workspace as timestamped Markdown and JSON.
- **Placement.** The logic lives on the server side next to matching (which issue 03 moves to the domain layer). Thin entry scripts outside the source tree only parse flags; they get their own lint allowance.
- **Glossary.** No change; "expected outcome" stays tool vocabulary.

## Agent Brief

**Category:** enhancement
**Summary:** Add an opt-in tool that measures matching accuracy against the job seeker's labelled vacancies

**Current behavior:**
Matching (structured checks, then decision model questions) is tested only with fake models. Nothing measures how often its Match outcome agrees with the job seeker's judgement. The probability and skill-coverage bands are uncalibrated.

**Desired behavior:**
- **Capture command.**
  - Takes a workspace, a vacancy URL, an expected Match outcome, optional expected criterion results and an optional note.
  - Resolves the URL to a job reference through the search sources; a URL no source claims is refused with a clear message.
  - Fetches the vacancy detail and stores one JSON file per vacancy in an evaluation folder of the workspace: the detail snapshot plus the label, versioned.
  - On first capture, stores a snapshot of the candidate's matching inputs (search configuration and profile skills) for the set.
  - Re-capturing an existing vacancy without the relabel flag is refused; with it, the label is replaced and the snapshot kept.
- **Run command.**
  - Takes a workspace and a required cost cap.
  - Runs real matching on every stored vacancy against the candidate snapshot.
  - Stops before the next call once reported cost reaches the cap. Calls of unknown cost count as reaching it unless explicitly allowed.
  - Per-vacancy evaluation errors are recorded and the run continues. Model outage, rate limiting or the cap stop the run, and a partial report is still written.
  - A dry-run mode uses a fake decision model and costs nothing.
  - Warns when the candidate snapshot differs from the workspace's current saved configuration.
- **Report.** Written to the workspace as timestamped Markdown and JSON, containing:
  - matching rules version, decision model identity, and the model reported in responses, with any mismatch flagged;
  - three-outcome confusion matrix;
  - agreement overall and excluding needs-clarification;
  - per-criterion confusion for labelled criteria;
  - per-vacancy rows: expected, actual, differing criteria, note;
  - total cost and the count of unpriced calls.
- **Isolation.** Neither command runs under `bun test` or CI, and nothing in the evaluation folder is committed.

**Key interfaces:**
- Search source contract: an optional "job reference from URL" capability. LinkedIn implements it for its job view URLs.
- The existing job detail schema validates stored snapshots. `matchJob` and the `DecisionModel` port (including its identity, from issue 14) are used unchanged.
- The search workflow's existing distinction between priced and unpriced calls, and its failure policy, are reused for the cost cap and error handling.
- Evaluation logic sits inside the existing architecture boundaries. Command entry points only parse flags and are allowed by lint.

**Acceptance criteria:**
- [ ] Capture stores a validated snapshot and label for a URL a source claims, and refuses unknown URLs and unflagged re-captures.
- [ ] Relabel replaces only the label.
- [ ] A run over the committed fictional sample set with a fake decision model produces the expected confusion matrix, agreement figures, per-criterion confusion and per-vacancy rows (offline test).
- [ ] A per-vacancy evaluation error appears as an error row and is excluded from agreement; an outage stops the run with a partial report (offline test).
- [ ] The cost cap stops the run before exceeding it, and unpriced calls stop it unless allowed (offline test).
- [ ] The report flags a candidate snapshot that differs from the current configuration, and a reported model that differs from the requested one.
- [ ] `bun test` and CI never invoke the commands or need credentials or network.
- [ ] Typecheck, lint, tests and build pass.

**Out of scope:**
- Collecting and labelling the real set, running the baseline, changing bands or the matching rules version (issue 35).
- Any UI for capture or labelling.
- Changing matching behaviour.
- Committing real vacancy text, reports or the job seeker's profile.
