# 03 — Move search sources, matching and their vocabulary out of `shared/` into a domain layer

Status: ready-for-agent
Type: task
Blocked by: 19, 01
Spec: [domain-layer spec](../../domain-layer/spec.md)

`web/src/shared/` mixes generic code (UI kit, `http`, `lib`) with domain components: `shared/search-sources/` (scraping adapters and registry) and `shared/ai/` (provider adapters). Matching lives in `modules/search/server/matching/` although its main consumer is the applications workflow, which receives it through dependency injection.

Proposal: introduce a domain layer (for example `src/domain/search-sources`, `src/domain/ai`, `src/domain/matching`) that features may import and that never imports features, and keep `shared/` for generic code only. Extend the ESLint boundary rules accordingly and update the README architecture and extension sections.

Pure move: no behaviour change. Done when the suite, typecheck, lint and build pass and the boundary rules cover the new layer.

## Comments

### Scope extension — 2026-10-23

A responsibility review found matching concepts scattered because they have no home:

- `shared/match-outcome.ts` (the criteria → Outcome rule) is matching domain logic placed in `shared/` so both Search and Applications can use it.
- `shared/compensation.ts` (contract types, currencies, pay periods) is domain vocabulary, not a generic utility.
- `modules/applications/model/contracts.ts` re-declares Search's `MatchResult` as `matchSchema`, kept in step only by a type check in `workflow.ts`, because modules cannot share runtime schemas.

Include these in the move: put the Outcome rule, the match result schema and the compensation vocabulary in the matching (or a small `domain/compensation`) part of the new layer, import the single match result schema from Applications and delete the mirrored `matchSchema` and its type-equality check. Stored `applications.json` and search memory formats must not change.

### Documentation requirement — 2026-10-23

This issue changes the architecture's layering, so record it as ADR 0011 in `docs/adr/` (context, the layer's contents and import rules, and why `shared/` stays generic), following ADRs 0005–0010. Update `CONTEXT.md` for any domain terms whose home or name changes, and the layer description in `web/README.md`'s architecture rules. The final layer name chosen here is what issues 17, 20 and 21 use.

### Triage — 2026-10-24

> *This was generated by AI during triage.*

Redundancy check: not implemented. There is no `src/domain/`; `shared/` still holds `ai/`, `search-sources/`, `match-outcome.ts` and `compensation.ts`; the only lint rule for `src/shared` is that it never imports features. No prior rejection.

Two facts found in the code shaped the decisions:

- Matching depends on the Search module at runtime: it imports the published search preferences schema and the seniority, position type and work arrangement enums from Search's model.
- Applications' `matchSchema` is not a plain mirror: its outcome is narrowed to `match | needs-clarification`, because only accepted vacancies become applications.

Decisions from grilling:

- **Name.** The layer is `src/domain/`.
- **Parts.** Three parts:
  - `search-sources`: contracts at the root, adapters and the registry under `server/`;
  - `matching`: client-safe contracts at the root (criterion result, match result, accepted match result, the Outcome rule, the published search criteria schemas), and the engine under `server/` (structured checks, questions, `matchJob`, the decision model, `MATCHING_RULES_VERSION`, and the evaluation module from issue 01);
  - `vocabulary`: contract types, currencies, pay periods and work location arrangements.
- **Adapters stay with their part** under `server/`. The existing server-import rule keeps them out of client code; a separate adapters layer is not introduced.
- **AI providers stay in `shared/ai`.** ADR 0005 made them domain-free (instructions, text and a schema in; no job-search vocabulary), so they meet this issue's own definition of generic code. The title is corrected accordingly.
- **Search criteria.** Only the published search criteria schemas move (target position, salary band, settings, search preferences). Draft schemas and empty values stay in the Search module, which keeps drafts, persistence and the editor.
- **Vocabulary is deduplicated.** The source contracts derive their pay period, contract type and work arrangement enums from `domain/vocabulary`, adding `unknown` where they need it. Their currency stays any three-letter code. Values do not change.
- **Match result.** The domain exports the full match result and the accepted match result. Applications imports the accepted one; the mirrored `matchSchema` and the `Same<>` check are deleted.
- **No re-exports.** Every consumer imports from `domain/` directly, including the compensation enums Search re-exports today.
- **Import rules**, each with allowed and forbidden cases in the ESLint config test:
  - `domain/` never imports `modules/` or `app/`, not even type-only;
  - `shared/` never imports `domain/`;
  - `modules/` and `app/` may import `domain/` at runtime;
  - a domain part may import another part's contracts, never its `server/` code;
  - the server rule applies inside `domain/` unchanged.
- **Order.** After 19 (its fixtures prove nothing changed on disk), 14 and 01 (the evaluation module moves with matching). Issues 10 and 12 follow this one.
- **Glossary.** No change: no domain term changes name or meaning.
- **Related edits made now.** Issue 17's layer section and the AI exemption path, issue 12's Search row, and issue 01 and its spec now say "next to matching" instead of naming the Search module.

## Agent Brief

**Category:** enhancement
**Summary:** Give search sources, matching and their shared vocabulary a domain layer, so `shared/` holds only generic code and Applications uses the one match result schema

**Current behavior:**
Search sources and their adapters sit in the generic shared folder. The Outcome rule and the compensation vocabulary sit there too, as loose files, only so Search and Applications can both reach them. Matching lives inside the Search module although the search workflow in Applications is its consumer, and it reads the Search module's published criteria schemas. Applications cannot share Search's runtime match result schema, so it keeps a narrowed copy, kept in step by a compile-time equality check. Work location arrangement, pay period and contract type values are declared separately in the source contracts and in the search criteria.

**Desired behavior:**
- A domain layer exists beside `shared/` with three parts:
  - search sources: contracts at the root, adapters and registry server-only;
  - matching: client-safe contracts (criterion and match results, the accepted match result, the Outcome rule, published search criteria schemas) and a server-only engine (structured checks, questions, the matcher, the decision model, the matching rules version, the evaluation tool's logic);
  - vocabulary: contract types, currencies, pay periods, work location arrangements.
- `shared/` keeps only generic code, including the AI provider adapters, which stay where they are.
- The Search module keeps search configuration drafts, persistence and the editor, and imports the published criteria schemas from the domain layer.
- Applications imports the accepted match result schema from the domain layer. Its own copy and the equality check are gone.
- Source contracts derive their enumerations from the vocabulary part and add `unknown` where needed. No value changes.
- Consumers import from the domain layer directly; no re-exports remain.
- Lint enforces:
  - the domain layer imports no feature module or app code, including type-only imports;
  - shared code imports nothing from the domain layer;
  - a domain part imports only other parts' contracts, never their server code;
  - features and the app may import the domain layer at runtime;
  - the existing server-only rule holds inside the domain layer.
- ADR 0011 records the layer: context, its parts, the import rules, why `shared/` stays generic and why AI providers stay in it.
- The README's architecture rules and its "Adding a source" and matching paths describe the new layout.

**Key interfaces:**
- No public behaviour, API route, event or stored format changes. Only import paths move.
- The match result and accepted match result schemas are the single source for Search and Applications.
- The matcher, the decision model port (with its identity from issue 14), the criteria digest inputs and the search source contract keep their signatures.

**Acceptance criteria:**
- [ ] The domain layer holds search sources, matching and vocabulary as described; `shared/` no longer holds the Outcome rule, compensation vocabulary or search sources.
- [ ] Applications has no mirrored match schema and no type-equality check, and uses the domain's accepted match result.
- [ ] Source contracts and search criteria take their shared enumerations from one place.
- [ ] The stored-format and digest fixtures from issue 19 pass unchanged.
- [ ] The lint config test has allowed and forbidden cases for every new import rule.
- [ ] ADR 0011 exists, and the README's architecture and extension sections match the layout.
- [ ] Tests, typecheck, lint and build pass.

**Out of scope:**
- Moving the AI provider adapters.
- Any behaviour change, rename of public symbols (issue 12) or decision model port/adapter split (issue 10).
- Lint rules beyond the layer rules above (issue 17).
- Glossary changes.
